Версия: 24 ноября 2026 года, этап 7. Статус: подготовлено, **размещение ещё не выполнялось**: проект на Railway не создан, настоящий бот и вход через Telegram на сервере не проверялись.

Связанные документы: [план разработки](./План%20разработки%20Telegram-бота%20и%20веб-кабинета.md) (раздел 9 — расценки Railway, раздел 11 — юридический риск 152-ФЗ, который нужно закрыть **до** подключения реальных учеников).

## 1. Что разворачивается

Один сервис и одна база PostgreSQL в одном проекте Railway:

| Часть | Как устроено |
| --- | --- |
| Сборка | `Dockerfile` в корне: двухэтапная сборка на `node:22-alpine`, в образ попадают только `dist/` и зависимости для работы. Секреты, `.env*`, тесты и данные разработки исключены `.dockerignore`. |
| Настройки Railway | `railway.json`: сборка по Dockerfile, миграции перед запуском (`preDeployCommand`), запуск `node dist/src/main.js`, проверка `/health`, перезапуск при сбое. |
| Миграции | `node dist/scripts/db-migrate.js` (то же, что `npm run db:migrate:prod`). Выполняется перед каждым запуском новой версии; уже применённые миграции пропускаются. Если миграция упала, новая версия не запускается, работает прежняя. |
| Бот | Только webhook: при `NODE_ENV=production` опрос запрещён настройками. Сервис сам регистрирует webhook `WEBHOOK_BASE_URL/telegram/webhook` (по умолчанию `WEB_BASE_URL`) с секретом `WEBHOOK_SECRET`; запрос без верного заголовка `X-Telegram-Bot-Api-Secret-Token` получает 401 и ничего не обрабатывает. |
| Проверка готовности | `GET /health`: 200 `{"status":"ok"}`, если база отвечает, иначе 503. Railway переключает трафик на новую версию только после 200. |
| Журнал | Строки JSON в stdout: `level`, `message`, `time`, `service`, у ошибок — `err` со стеком, у запросов — `reqId`. Cookie, CSRF, секрет webhook, токены и коды скрываются. Пользователь видит только общий текст ошибки. |
| Остановка | По SIGTERM сервис останавливает планировщик и очередь уведомлений, закрывает сервер и соединения с базой. |

Во время смены версии Railway какое-то время держит старую и новую копии одновременно. Это безопасно: уведомления разбираются с блокировкой строк (`FOR UPDATE SKIP LOCKED`), квест и напоминание защищены уникальными ограничениями, повторная доставка события Telegram отсекается по `update_id`.

## 2. Переменные окружения сервиса

Полный список с пояснениями — в `.env.example`. На Railway задаются в разделе Variables сервиса:

| Переменная | Значение на Railway |
| --- | --- |
| `NODE_ENV` | `production` |
| `BOT_MODE` | `webhook` |
| `BOT_TOKEN` | Токен **отдельного** бота для пилота (не того, что используется при разработке). |
| `WEBHOOK_SECRET` | Случайная строка 32–256 символов `A-Z a-z 0-9 _ -`, например `openssl rand -hex 32`. |
| `APP_SECRET` | Случайная строка не короче 32 символов, например `openssl rand -base64 48`. **Не менять после запуска пилота**: выданные ссылки и коды перестанут работать. |
| `WEB_BASE_URL` | `https://<имя-сервиса>.up.railway.app` — адрес, который Railway выдаст в Settings → Networking → Generate Domain. |
| `WEBHOOK_BASE_URL` | Не нужен: по умолчанию совпадает с `WEB_BASE_URL`. |
| `TELEGRAM_LOGIN_CLIENT_ID`, `TELEGRAM_LOGIN_CLIENT_SECRET` | Из BotFather, раздел Login Widget для бота пилота. |
| `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` — ссылка на переменную базы того же проекта (внутренняя сеть Railway). |
| `LOG_LEVEL` | Не обязательно, по умолчанию `info`. |
| `PORT`, `HOST` | Не задавать: `PORT` выдаёт Railway, адрес при webhook — `0.0.0.0`. |
| `DEV_LOGIN_TELEGRAM_ID` | **Не задавать**: при `NODE_ENV=production` сервис с ней не запустится. |

Сервис проверяет настройки при запуске и завершается с понятным сообщением, если чего-то не хватает (значения секретов в сообщение не попадают).

## 3. Первое размещение по шагам

Эти шаги выполняет владелец аккаунта Railway. Разработчик их не выполнял.

1. **Юридическая проверка.** До подключения реальных учеников получить заключение юриста по 152-ФЗ (раздел 11 плана). Технически сервис не привязан к Railway: тот же образ запускается у российского провайдера.
2. **Бот для пилота.** В BotFather создать отдельного бота (или выбрать существующий для пилота), сохранить токен.
3. **Проект Railway.** Аккаунт с тарифом Hobby и способом оплаты. New Project → Deploy from GitHub repo → репозиторий проекта (ветка с этапом 7). Railway найдёт `railway.json` и `Dockerfile` сам.
4. **База.** В проекте: New → Database → PostgreSQL. В настройках базы включить резервные копии тома (Backups, см. раздел 5).
5. **Адрес.** В сервисе: Settings → Networking → Generate Domain. Получится `https://<имя>.up.railway.app`.
6. **Вход через Telegram.** В BotFather для бота пилота: Login Widget → адрес кабинета `https://<имя>.up.railway.app` и адрес возврата `https://<имя>.up.railway.app/api/auth/telegram/callback`. Сохранить Client ID и Client Secret.
7. **Переменные.** Заполнить переменные из раздела 2. После сохранения Railway запустит сборку.
8. **Сборка и запуск.** В журнале развёртывания должны быть: сборка образа, `Миграции применены` (pre-deploy), затем записи `Webhook зарегистрирован` и проверка `/health` с ответом 200.
9. **Проверка webhook.** В браузере: `https://api.telegram.org/bot<токен>/getWebhookInfo` — `url` равен `https://<имя>.up.railway.app/telegram/webhook`, `last_error_message` пуст. (Ссылку с токеном никому не пересылать.)
10. **Роль преподавателя.** Выдать роль Telegram ID преподавателя командой на сервере: в Railway открыть сервис → вкладка с консолью (или `railway ssh` из Railway CLI) и выполнить `node dist/scripts/admin-role.js set-teacher <telegram_id>`. Действие запишется в журнал администратора.
11. **Сквозная проверка вручную** (раздел 6 этого документа) на одном тестовом ученике.
12. **Резервная копия вне Railway** (раздел 5) — сразу после первого запуска и затем по расписанию.

Обновление: новый коммит в выбранной ветке → Railway собирает образ, применяет миграции, переключает трафик после `/health`. Откат: в Railway → Deployments → Redeploy предыдущей версии. Миграции вниз не откатываются; все миграции проекта только добавляют, поэтому прежняя версия кода работает с новой схемой — но перед откатом это нужно проверить по списку изменений.

## 4. Журнал ошибок

- Railway → сервис → Logs. Фильтр по уровню: `@level:error`; по запросу: `@reqId:req-1a`; по событию Telegram: `@updateId:123`.
- Ошибка кабинета: пользователь видит «Что-то пошло не так. Попробуйте ещё раз.», в журнале — `Ошибка запроса кабинета` со стеком и `reqId`.
- Ошибка обработки события бота при webhook: в журнале `Необработанная ошибка запроса`, Telegram получает 500 без подробностей и повторяет событие; повтор безопасен.
- Недоставленные уведомления: `Часть уведомлений не доставлена` (заблокировавшие бота ученики отмечаются в базе), сбой цикла — `Ошибка обработчика уведомлений`, сбой планировщика — `Ошибка планировщика напоминаний`.
- Срок хранения журнала на Railway ограничен тарифом. Если журнал нужен дольше, его можно направить во внешний сервис (Railway Log Drains) — для пилота не требуется.

## 5. Резервные копии

Нужны оба вида: встроенные копии Railway защищают от ошибок в данных, внешняя — от потери проекта или тома.

**Копии тома Railway.** База → Backups → включить расписание. По [документации Railway](https://docs.railway.com/volumes/backups): ежедневные хранятся 6 дней, еженедельные 27, ежемесячные 89; при удалении тома копии удаляются, восстановление — только в том же проекте. Восстановление — кнопкой Restore у нужной копии (Railway создаёт том из копии и подключает его к базе).

**Внешняя копия `pg_dump`.** Скрипт `scripts/db-backup.sh` (`npm run db:backup`):

```bash
# Публичный адрес базы: Railway → Postgres → Connect → Public Network (DATABASE_PUBLIC_URL).
DATABASE_URL='postgresql://...' BACKUP_KEEP=30 npm run db:backup -- /путь/к/зашифрованному/диску
```

- формат `pg_dump --format=custom`, файл `english-bot-<дата UTC>.dump`; после записи скрипт проверяет, что оглавление файла читается, недописанный файл не остаётся;
- папка создаётся с доступом только для владельца (в копии — персональные данные учеников), хранится не больше `BACKUP_KEEP` последних файлов;
- нужен `pg_dump` той же основной версии, что и сервер Railway, или новее (`PG_BIN` — папка с ним);
- запускать по расписанию на компьютере ответственного (cron/launchd) или отдельным cron-сервисом Railway с отправкой файла во внешнее хранилище — выбор и хранилище нужно согласовать с заказчиком (раздел 10 плана). Рекомендуется раз в сутки.

**Восстановление из `pg_dump`** — только в пустую базу, сначала на копии:

```bash
createdb -h <хост> -U <пользователь> english_bot_restore
pg_restore --no-owner --no-privileges --exit-on-error --dbname='postgresql://.../english_bot_restore' english-bot-....dump
```

Затем сверить число строк в основных таблицах (`users`, `student_links`, `attempts`) и переключить `DATABASE_URL` сервиса на восстановленную базу. Локально этот цикл (копия → восстановление в новую базу → сверка) проверен 24 ноября 2026 года на базе e2e.

## 6. Ручная проверка после размещения

1. Открыть `https://<имя>.up.railway.app`, войти через Telegram аккаунтом преподавателя. Аккаунт без роли видит «Нет доступа» и свой Telegram ID.
2. «Ученики» → «Добавить ученика» → ссылка. Открыть её тестовым аккаунтом ученика, подтвердить, ввести код в кабинете.
3. «Подборки» → создать подборку из 5–6 слов (или импорт), выдать ученику; в боте пришло уведомление.
4. В боте пройти тест с одной ошибкой и одной двойной ошибкой; открыть «Сложные слова».
5. В кабинете: карточка ученика → «Открыть результаты» — занятие, обе попытки, сложное слово; «Скачать CSV» открыть в Excel: русский текст читается, столбцы разделены.
6. Подборка → «Результаты по подборке»; главная → «Последние результаты».
7. В журнале Railway нет записей уровня `error`.
